# Wildlands MMO wiki maintenance

Use this guide when reading or changing the wiki, its documents, visual boards, or tuning sheets. The `claude/mmo-overhaul` checkout is the live canon line; `main` is the historical archive. Confirm the checkout and pending changes before editing, especially when another agent is active.

## Choose the right source

| Material | Authority | How to use it |
| --- | --- | --- |
| Current implementation | Running code and game data, summarized in `docs/current/` | Cite the owning file and key or function. A data row alone does not prove the behavior is reachable or complete. |
| Vision | Owner-approved experience and rules in `docs/vision/` | Cite the section that records the decision. Describe intended behavior without claiming it is shipped. |
| Proposal or open question | Clearly marked candidate in a vision document or an owner draft | Keep it labeled as proposed or unresolved until the owner approves it. Do not turn a candidate percentage into a confirmed rule. |
| Archive or reference | Historical material on `main`, or build references retained on the canon line | Use for provenance or investigation. Check newer sources before relying on an old claim. |

The vision docs contain both owner-confirmed decisions and proposed details. Preserve those labels at the section and number level. If evidence is missing or sources disagree, mark the item unknown or conflicting and link both sources. Ask the owner for a design decision instead of inventing one.

## Read the minimum useful context

1. Identify the system and whether the question concerns the current build, intended design, or history. Start with the relevant index in `docs/current/README.md` or `docs/vision/README.md` and the specific page or section.
2. For implementation, inspect the cited code or data and verify the behavior or value that matters to the task. For vision, read the exact owner decision and its proposal labels. Search the archive only when provenance, an unresolved conflict, or a missing detail requires it.
3. Cite the exact path and section, function, or data key in your work. State gaps rather than loading the full archive into context. Keep a short handoff containing decisions and evidence, not copied source documents.

## Update and archive documents

1. Find the existing authoritative page before writing. Update it in place; use links for related material instead of duplicating live facts. Add a focused page only when it covers a distinct system and link it from the appropriate index.
2. For current pages, document only behavior supported by the current code or data. Update the page with the implementation change, and include the path and relevant key or function for each tunable number. Do not hand-edit generated pages; update their source and use the generator after checking the sheet safeguard.
3. For vision, distinguish an owner-confirmed decision, a proposal, and an open question. Preserve the owner's wording where the distinction matters. When a decision changes, update its authoritative section and any affected links; do not silently rewrite historical decisions as if they were always true.
4. Before archiving a page, identify its replacement, check inbound links and build consumers, and preserve unique decisions or evidence in the appropriate live source. Put the retired version on the archive line with a historical label and a pointer to its replacement. Verify the archived copy and remove the retired live copy without overwriting an existing historical file. A `git mv` cannot move a file between separate worktrees or branches; coordinate the two branch commits and preserve both checkouts' unrelated work.
5. Verify links, status labels, source citations, and generated output. Record what changed, validation, unresolved conflicts, and the next agent's task in the required orchestration report.

Never move or delete a build-consumed reference merely because it looks old. Follow its actual consumers and the folder ownership rules in `AGENTS.md` first. Existing archive material is a historical record, not current context to rewrite.

## Review and remove bloat

1. Define the problem: disk or export size, duplicate implementation, or context a task needlessly loads. Measure it and record the candidate paths.
2. Check Git status, ignored files, active agents, and ownership. Preserve unrelated work, historical records, source art, and owner drafts. Treat matching bytes as a lead, not proof a file is disposable.
3. Find consumers in scenes, scripts, manifests, generated data, import settings, build tools, and wiki links. For docs, identify the authoritative page and preserve distinct decisions, approval status, links, and requirements of standalone prompts. Consolidate duplicated live facts by linking to their source.
4. Prove the safety claim with the real generator, importer, game, or affected tests in a temporary copy when possible. Check derived files and import settings as well as visible output. If a consumer or recovery path is uncertain, leave the candidate in place and report the evidence needed.
5. Make the smallest reversible change, update affected links or documentation, run relevant checks and `tools/smoke.sh`, and report what changed, evidence, remaining risks, and how to recover it.

## Images and visual boards

Separate screenshots of the current build from the art and UI vision boards. For each image, record a useful caption, source path or URL, date or build revision when known, and its status: current capture, owner-approved direction, proposal, or external reference. Link the image to the system or design decision it illustrates. A screenshot proves only what it shows at that build; an image on a vision board is not automatically an approved design. Keep the original file and reference it rather than copying it into multiple documents. UI references pasted in chat without a file follow the durango-prompts convention: a dated note ("owner screenshot, 2026-10-27, not saved to disk") plus the orchestrator's reading, filed with the system it illustrates, cross-referenced rather than duplicated elsewhere.

The art board's 3D model previews are generated from the GLB files under `game/assets` (`list_models` in `tools/docs_wiki/docs_wiki.py`) and show the asset files themselves, not the build. The list contains only files with mesh geometry; a species' clip files — animation-only libraries and per-clip mesh exports alike — are folded into the Animation choices of that species' rig entry. Per-species animation design status is recorded in `tools/docs_wiki/model-animations.json` from owner decisions; the Animation list marks planned animations with no file yet, and cancelled designs (with the reason on hover). `tools/audit_gaits.py` checks the same clip data offline — sampler-time validity, stance-foot drift against rig facing (backwards-walk detection), and run-vs-walk duplication. A playable preview is not evidence that the current build loads the asset or plays that animation. Model entries can also carry an owner mark, stored beside the article marks in `state.json` (under `models`, keyed by asset path): the viewer's Mark row edits them through `/api/mark`, seeded suggestions keep `by:"seed"` until a person saves over them, and the asset dropdown suffixes the mark status. The Art board's reference cards are curated in `tools/docs_wiki/boards.js`; its two survivor cards are neutral Blender renders produced offline by `tools/render_model_cards.py` into `artifacts/wiki/`, and the per-species cards point at the models' generation-input sheets under `game/assets/creatures/*/sheet.png`. The mounted view is a default-off toggle: `composeMount` in `tools/docs_wiki/models.js` parents the saddle and survivor into the rig using the species `mount.json` `rider_in_mount`, applies `scale.game_m_per_source` when the GLB ships at source scale (tyrannosaurus ships at game scale and carries none), counter-scales the rider root by `1/factor` so the mount's game-size scale does not leak into the survivor (the engine's `_rider_offset` in `creature_view.gd` cancels the same factor, and `equip_mount_lab.gd` fails a species whose rider world scale drifts from 1.0), and plays the survivor's seated `mount_idle` as the rider clip.

## Phase map (roadmap)

`tools/docs_wiki/phase-map.json` is the authored truth for the Roadmap tab: a `goal` sentence, phases numbered 0 (foundations everything else relies on) up to 5 (polish and tuning), and per-phase features with `id`, an authored `status` (`done` / `next` / `later` / `decided-against`), `depends` edges to other feature ids, and a `source` path into a repo document that shapes the feature. Dependency results follow from the docs, not from preference: a feature is buildable when its dependencies are done, and the tab computes "next up" as `next` features whose dependencies are all `done`.

Statuses are a seeded snapshot, not a verdict. Changing a status on the Roadmap tab is a mark — it posts `/api/phase` and lives in `state.json` under `phases` (keyed by feature id, `by:"mark"`, `by:"mark"` uses the field name `note`, unlike doc and model marks which use `notes`); `↺` clears a mark back to the authored status. Structural edits — adding a feature, adding a phase, retitling, re-linking dependencies, or retiring an idea permanently — are hand edits to `phase-map.json`, and the file must stay valid: unique kebab-case ids, resolvable dependencies with no cycles, statuses from the vocabulary, and `source` paths that exist in this checkout. `tools/docs_wiki/test_phase_map.py` enforces this on the authored file and on hand-edited variants; the server re-validates on every read and reports a broken file with a 500 plus the reason instead of rendering it. When a build package lands, set its phase-map statuses to `done` with a note naming the merge commit, so the "next up" list stays honest.

The tab renders phases reading downward from Phase 0 so the page starts with the foundations every feature relies on and descends toward polish and tuning, with a per-phase done bar and blocked hints on `next` features whose deps are unfinished. Each phase is a `<details>` accordion, **collapsed by default** (the expand button reads "Expand all" on a fresh load): the header row (number, title, done bar, count) toggles the block, a Collapse all / Expand all button sits in the chip row, and the state is kept while you edit statuses in-page. Clicking a dependency chip auto-expands the target phase (if collapsed) and scrolls to that feature. Collapsed blocks still count toward the done bars and the chip counts. `decided-against` rows stay visible (struck through) so future plans do not re-propose retired ideas. `plan-map` status changes never touch documents; they are curation like the doc and model marks.

## Plan review (reconcile) and structure refactor

The **Review a plan** tab reconciles a ChatGPT-authored plan against the canon docs. `/api/plan/analyze` runs the configured local AI (OpenCode CLI, sandboxed, all tool permissions denied) over the plan plus bounded excerpts from `docs/current` and `docs/vision` only. Its output is untrusted and is checked: every claim carries citations that must match real excerpts, every proposed edit must occur exactly once in the cited document, and no edits are offered while conflict questions remain open. Answering the questions re-sends them as decisions and produces a clean proposal. Provider limits surface as a plain 503 ("free model limit reached"); the client shows it and the plan is untouched.

Applying a proposal is `/api/plan/apply`: exact `old_text → new_text` replacements into `docs/vision/*.md` only, pinned to the document's SHA-256, applied through `tools/docs_wiki/plan_edits.py` — verified unique occurrences, no overlaps, an atomic temp-file write re-checked against the revision before and after, and a permanent byte-exact backup of the original under the repo's git dir (`wildlands-wiki-backups/<sha>.md`). A changed document returns 409 and the proposal must be re-run.

The **Review document structure** section drafts a split of an oversized vision document (`/api/plan/refactor`): lossless level-2 sections as sibling files plus a heading-mapped index, with warnings for anything judgment-heavy (fragment links that leave a section, existing destinations). Applying an approved split (`action:"apply"`) goes through `plan_refactor.apply_split`: the reviewed proposal is never trusted — the split is recomputed from the current bytes and compared in full (revision, preamble, every section title/content/lines, index preview), all destinations must be absent, the original is backed up as `<sha>--split.md`, sections are written before the source becomes the index, and a write failure rolls back the written sections and leaves the source unchanged. Cross-document incoming links still need a human or agent pass after applying; the proposal's warnings name the suspects.

Post rules: `/api/plan/*` accepts only same-origin JSON posts from the wiki itself. `/api/state` rejects (409) a docs store that would shrink the existing curated marks unless `allow_shrink:true` is sent — a partial client payload must not eat curated doc marks, and the same guard preserves `models` and `phases` keys that a stale article payload omits.

## Tuning and review

The shipped values live in game code and data. Editable sheets and wiki drafts are a way to propose changes; they are not proof that the game uses those changes. For every proposed edit retain the source file, stable row or key, field, original value, new value, units or percentage scale, and the source revision or baseline. Keep trait names, effects, ranges, and related identifiers connected to their actual consumers. Treat fields not yet represented in a sheet as coverage gaps, not as nonexistent tunables.

Export or present a diff for review before applying a tuning update. Check that the baseline still matches, validate types, bounds, references and cross-field ranges, then apply the accepted changes through the appropriate data or code workflow. Run the relevant tests and the repository smoke check, regenerate affected current pages without overwriting unsynced edits, and report the result. If validation fails, report which files were written and leave the proposal available for review; do not claim the update shipped.
